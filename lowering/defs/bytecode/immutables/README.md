# Immutable parity fixtures

The eight required word-immutable parity fixtures cover declaration-order offsets,
constructor arguments, sender addresses, constructor reads, and a runtime-only
internal function in a program with a constructor. `oracle/` contains annotated
AST/layout inputs and deploy/runtime bytecode generated by pinned Vyper
0.5.0a4 cd74ce4f. Its provenance records source/output hashes and compiler
settings: optimization NONE, experimental code generation, Prague, and no
bytecode metadata.

Additional sources retain constructor/internal reads, multi-word strings,
bytes and arrays, the task's supplied residual witnesses, and the runtime-only
internal-function control. They are diagnostic inputs; the default HOL fixture
theory asserts the eight entries in `parity-fixtures.txt`. Public getters and
the residuals assigned to #543, #544, #558 and #560 remain separately classified.

The retained [extended results](diagnostics.json) cover the other 33 sources:
19 exact deploy/runtime matches and 14 dependency residuals. Every source is
accepted by both checker modes, and every compilation evaluates to `SOME`.

| Dependency | Residual witnesses |
| --- | --- |
| #543, constant folding | i12, p29 |
| #544, constructor locals | m03, m07 |
| #558, struct/nested-array access | i04, p28, m10 |
| #560, dynamic-array literal ordering | i03, p30, m05, m06 |
| #565, public getters | i05, i09, i13 |

`m03_imm_string_read_in_ctor` is an additional #544 witness beyond the task's
original residual list. Its runtime matches, while its deploy differs because
`compile_generate_deploy` omits `reserve_local_ptrs`: the `AnnAssign` local
keeps a fixed `MemLoc`. The #544 task explicitly owns both `AnnAssign` and `For`
constructor-local allocation. No getter, folding, constructor-local, or nested
access fix is included here. The JSON records byte counts, first differences,
source hashes, and compiler-definition hashes for this classification.

With the pinned Vyper environment on PATH and its Python interpreter selected:

```sh
python lowering/defs/bytecode/memory_store_witnesses.py prepare \
  --corpus immutables --fixtures /tmp/immutable-oracle --check
holbuild build evalCompilerImmutablesTheory
```

The existing checked-frontend fixture library validates both source checker
modes, then compares both HOL byte arrays with the independent oracle. The
diagnostic mode retains individual checker/compiler outcomes and bytecode:

```sh
python lowering/defs/bytecode/memory_store_witnesses.py probe \
  --corpus immutables --fixtures /tmp/immutable-oracle \
  --output /tmp/immutable-hol
```

The separate [padding regression](../immutable_padding_probe.py) executes
constructor and runtime bytecode in a Prague EVM. It demonstrates why the
installed-code relation must allow different unused padding for identical
source immutable values. See the [checked HOL probe](../../../proofs/immutableReachableProbe.md)
for its evidence and scope.

Installed code uses an actual section witness, related to source immutable
values by [immutables_section_rel](../../../proofs/immutableSectionRelScript.sml).
The [byte predicate](../../immutableValueScript.sml) allows unused string/byte
capacity and inactive dynamic-array elements to vary, while checking omitted
sparse-array elements against their defaults. The canonical encoder remains
a witness for the relation.

The constructor-copy and staging proofs transport actual bytes without a
full-source-capacity or canonical-padding premise. Their ordinary typing,
freshness, allocation and separation conditions remain explicit. The
[code-layout bridge](../../../proofs/immutableCodeLayoutScript.sml) uses the
computed final `code_end` header and retains the assembler's existing
`asm_encoding_wf` condition; no new top-level e2e premise is introduced.

The Prague EVM regression checks p23's returned code as the 82-byte runtime
followed by the 32-byte encoding of 42, then checks `get() = 42`. The HOL fixture
theory also checks the source interpreter's deployment and subsequent `get()`.
The EVM probe runs constructor bytecode directly rather than a CREATE transaction.
